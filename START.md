# Практика. Две ветки — один результат

В этой практике вам предстоит объединить изменения, которые были независимо подготовлены в двух ветках проекта.

Проект содержит небольшой pipeline обработки результатов benchmark для LLM и агентных систем.

Обе доработки нужны в итоговой версии, однако они были разработаны независимо и могут конфликтовать между собой.

Ваша задача — корректно объединить изменения и сохранить работоспособность проекта.

## 1. Создайте рабочую ветку

Создайте собственную ветку от актуального `master`.

Название ветки должно соответствовать шаблону:

```text
student/<ваш_логин>
```

Например:

```text
student/ivanov
```

После создания ветки система автоматически:

- определит ваш индивидуальный вариант;
- подготовит данные benchmark;
- создаст две ветки с независимыми изменениями.

Все дальнейшие изменения выполняйте только в своей рабочей ветке.

Не изменяйте `master` и ветки `feature/*`.

## 2. Проверьте данные своего варианта

После подготовки задания в вашей ветке появится файл:

```text
data/benchmark.csv
```

Он содержит данные вашего индивидуального benchmark-варианта.

Посмотрите на структуру таблицы и названия столбцов.

Данные могут отличаться у разных студентов.

## 3. Найдите ветки своего варианта

В репозитории будут подготовлены две ветки вида:

```text
feature/vXX-a
feature/vXX-b
```

где `XX` — номер вашего варианта.

Обе ветки содержат полезные изменения одного benchmark pipeline.

Перед объединением изучите изменения в обеих ветках.

Обратите внимание не только на `src/benchmark.py`, но и на другие изменённые файлы.

## 4. Объедините первую ветку

Влейте изменения из:

```text
feature/vXX-a
```

в свою рабочую ветку.

Проверьте, какие изменения появились в проекте.

## 5. Объедините вторую ветку

После этого влейте изменения из:

```text
feature/vXX-b
```

в ту же рабочую ветку.

При объединении возникнет конфликт.

Разрешите его так, чтобы функциональность обеих веток сохранилась.

Важно: задача не сводится к удалению маркеров конфликта или механическому выбору одной из сторон. Изменения были разработаны независимо и могут использовать разные представления одних и тех же данных.

Итоговый код должен корректно учитывать смысл обеих доработок.

## 6. Проверьте зависимости проекта

Одна из веток добавляет библиотеку, необходимую для новой функциональности.

Убедитесь, что после объединения необходимые зависимости сохранились в:

```text
requirements.txt
```

Не добавляйте библиотеки в файл только ради прохождения проверки: зависимость должна соответствовать итоговому коду проекта.

## 7. Проверьте работу pipeline

Запустите итоговый код на данных:

```text
data/benchmark.csv
```

Убедитесь, что программа выполняется без ошибок и результат обработки выглядит осмысленно.

Особенно внимательно проверьте:

- изменения структуры данных;
- вычисляемые показатели;
- единицы измерения и диапазоны значений;
- граничные случаи.

## 8. Добавьте README

Создайте или обновите:

```text
README.md
```

Файл не должен быть пустым.

Кратко укажите:

- какие две доработки вы объединяли;
- в чём заключался конфликт;
- как вы сохранили функциональность обеих веток.

Достаточно нескольких содержательных строк.

## 9. Зафиксируйте результат

После разрешения конфликта:

1. проверьте изменённые файлы;
2. добавьте их в индекс;
3. создайте commit;

В истории вашей ветки должно сохраниться выполненное слияние.

Не заменяйте процесс merge простым копированием готового итогового файла.

## 10. Запустите проверку

Когда считаете работу завершённой, запустите workflow:

```text
Check student solution
```

Проверку запускайте для своей ветки:

```text
student/<ваш_логин>
```

Автоматическая проверка оценивает:

- корректность итогового benchmark pipeline;
- сохранение функциональности обеих веток;
- корректность обработки данных;
- историю изменений;
- наличие необходимых зависимостей;
- наличие непустого `README.md`.

Проверка оценивает итоговое состояние проекта и историю работы, но не требует конкретного способа разрешения конфликта.

## Важно

Не изменяйте:

```text
master
feature/*
```

Не пытайтесь обойти merge простым переписыванием `src/benchmark.py`.

Цель практики — пройти реальный процесс интеграции параллельных изменений и получить корректное итоговое состояние проекта.
